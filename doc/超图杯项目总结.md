## 超图下阶段想法

> 基于时空智能和数字孪生的化工园区危险气体监测和溯源系统

### 当前

- 坐标系还有米制坐标系（自己转化的）
- 超图只用到iserve发布瓦片数据、iportal制作数字大屏，idesktopx只用于把3d max建模的模型转化为三维瓦片数据，并没有做空间数据处理
- 现在的模型是一整个大模型，没有道路、交叉点、建筑物等矢量data
- 天气参数应该是实时变化的（接入和风天气api），而不是通过自己调整（存在“按照自己预设剧本进行演戏“的嫌疑）
- 没有用到supermap上的算法，如果supermap算法和自研算法有冲突，该用谁的？
- 粒子滤波扩散反演本质上是输出泄漏原点的概论密度，现在的作品是输出一个准确的点
- 移动端尚未开发



### 后续：

- 不管是三维还是二维（**二维地图绝不能去掉，反而要加强。** 让二维地图承载**所有空间分析算子**（缓冲区计算、路径分析），让三维场景只做**结果渲染**（云团、概率山峰））都要把坐标系真真切切的用CGCS2000国家大地坐标系或者是WGS84坐标系（取决于iserve上是什么坐标系）

> 让**二维地图做“后台计算引擎”，三维场景做“前台投影仪”**。
>
> 具体操作如下（以“疏散路径”为例）：
>
> 1. **交互触发（在三维里点）**：在三维场景里点击了一栋建筑，说“我要从这里疏散”。
> 2. **数据传递（给二维算）**：系统把点击处的**经纬度（或投影坐标）**抛给后台的二维地图引擎（SuperMap iClient2D 或 iServer 的二维网络分析模块）。此时，二维地图**并没有画面显示**，它只是在内存里利用**道路网络数据集（只有线，没有楼）**进行 Dijkstra 算法求解。
> 3. **结果返回（给三维画）**：二维引擎算出一条由 `[x,y]` 坐标串组成的路径（纯数学数组）。
> 4. **三维渲染（抬高显示）**：前端拿到这个二维坐标数组，给每个坐标点**强制赋一个固定的Z值（比如离地0.5米）**，然后调用 `Cesium.Polyline` 或 `iClient3D` 的线实体画在三维场景里。

- 用超图桌面软件把瓦片数据进行空间数据处理，第一阶段把道路网格分离出来，构建三维网络数据集并在iserve上发布为data数据，后续再将油管、建筑物、传感器等分离出来，作为data数据集用于在web端进行空间数据操作
- 废弃手动输入环境参数，接入真实可靠环境api进行实时数据调用，增加模型的可靠性
- 监控点位的缓冲区计算、路径规划算法可以用超图自带算法替代现有算法
- 用超图的热力点云代表三维空间中粒子滤波反演算法最终结果的概论密度，让评委看到的是一个溯源点位概论大小，而不是一个椭圆的置信区间或者精准点位
- 用超图的安卓版开发软件进行移动端开发，移动端最好是用三维地图，如果数据太大，移动端性能不行，可以考虑将三维场景转化为白模（亦或者用二维数据），移动端主要是做管理（人员、监控等）还有应急决策的联动

### 数据的封装

统一用FastAPI将算法进行封装，注意：封装后需要进行精度测试

#### 封装架构

所有算法封装在单体 FastAPI 服务（`algorithm/api_server.py`，端口 8000）中，采用「统一引擎入口 + 快捷端点」双层模式。算法不直接暴露，经 `engine/task_router.py` 按 `task_type` 字符串路由分发，既能被 HTTP 调用，也能被 Pyodide Worker 复用。

- 统一响应信封：`{code, ok, message, timestamp, requestId, data}`
- data 内自动注入 trace 元数据：`requestId`、`algorithm:{name,version,configVersion}`、`runtime:{costMs,worker}`、`inputSummary`、`grayRelease`（灰度发布）、`fallback`（降级标记）、`warnings`、`errors`
- 安全：`X-API-Key` 头鉴权（未配置密钥默认 503 拒绝）、CORS 白名单、DoS 防护（frameCount 钳制 [0,600]、gridStep 钳制 [5,100]、animationSteps 钳制 [8,200]）
- 错误处理：`ValueError→400`、未捕获→500、文件缺失→404，全部走统一 JSON envelope

#### 需要优化的地方

1. **入参弱类型**：端点入参用 `Dict[str,Any]` 而非 Pydantic `BaseModel`，FastAPI 自动生成的 OpenAPI 文档对请求体无 schema，前端只能靠手写 TS 类型对齐，易漂移。应改为 Pydantic Model + 响应模型，让 OpenAPI schema 成为前后端契约单一事实来源。

2. **契约测试不足**：5 个核心算法端点（diffusion/coarse-search/solve/particle-filter/evacuation）缺少端到端契约测试，当前只有 `test_api_server_http_semantics.py`、`test_service_config.py` 覆盖 HTTP 语义层。应补充各端点的输入输出 schema 断言，防封装格式漂移。

3. **YOLO 视觉检测未统一**：文档中提到的 8001 端口 YOLO 服务在本仓库无 FastAPI 实现，属于外部独立服务，未纳入统一信封与鉴权体系。应将其接入同一 `success_response`/`error_response` 信封与 `X-API-Key` 鉴权，或明确界定为外部依赖并文档化。

4. **验证报告非实时**：btex-validation 和 prairie-grass-source-validation 两个端点是读本地 JSON 文件，需离线脚本预生成。应考虑缓存失效提示、生成时间戳字段，或改为按需计算。

5. **溯源结果表达**：粒子滤波本质输出概率密度，当前只返回一个准确点 + 置信区间，未充分呈现概率分布。可补充后验概率热力网格字段，供三维热力点云可视化使用（呼应前文「用超图热力点云代表概率密度」的想法）。

6. **灰度/降级标记未实际驱动**：`grayRelease` 和 `fallback` 字段虽已注入响应，但代码中未看到实际触发降级或灰度分流的逻辑，目前是空壳元数据。应要么接入真实灰度路由，要么移除避免误导。
