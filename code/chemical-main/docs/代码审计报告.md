## 二、CRITICAL / HIGH 详述

### 【CRITICAL·1】四套园区锚点坐标并存，气象站坐标被当园区兜底

**位置**：`frontend/src/data/supermapGeoreference.js`、`frontend/src/components/SuperMapSceneViewer.vue`、`frontend/src/utils/clientSpatialQuery.ts`、`frontend/src/config/spatial-assets.4490.json`、`.env.development`

**现状**：同一概念"园区锚点"存在至少 4 套坐标值，散落 6 个文件：

| 锚点 | 经纬度 | 来源 | 含义 |
|---|---|---|---|
| `SUPERMAP_CGCS2000_ANCHOR` | 113.535771, 34.818673 | supermapGeoreference.js:31 | ✅ 当前正确（huangong S3M，pyproj 反算） |
| `ZHENGZHOU_STATION_57083` | **113.6650, 34.7178** | supermapGeoreference.js:18 | ⚠️ 郑州国家气象站（距园区 ~13km） |
| 旧 3D Tiles 锚点 A | 113.569463, 34.76965 | SuperMapSceneViewer.vue:671/691/696 硬编码 + CP0 注释 | ❌ 旧模型锚点（偏东 7.4km） |
| `SUPERMAP_ISERVER_DATA_ANCHOR`(D) | 113.53946126, 34.83164647 | supermapGeoreference.js:138 | iServer 数据集锚点（又一套） |
| spatial-assets.4490.json | 113.53576937, 34.81867209 | config/spatial-assets.4490.json:10 | ✅ 正确（更高精度变体） |
| `clientSpatialQuery` ANCHOR | 113.535771, 34.818673 | utils/clientSpatialQuery.ts:41 | ✅ 正确（与 CGCS2000_ANCHOR 一致） |
| `VITE_QWEATHER_LOCATION` | 113.6650, 34.7178 | .env:45、screen/index.vue:647 | = 气象站（天气用，但与园区锚点同名空间混淆） |

**最危险点**：`SuperMapSceneViewer.vue` 同时 import `ZHENGZHOU_STATION_57083`（line 221）并在 **line 7627**（`viewCenter || ZHENGZHOU_STATION_57083`）作相机视图兜底、**line 7654** 取其 altitude——一旦主 viewCenter 为空，相机/海拔回退到**气象站坐标（113.665,34.7178）**，距园区 13km。同时 line 671-697 硬编码旧 A 锚点 113.569463 共 6 处。

**触发场景**：3D 场景初始化时若 `threeTilesGeoreference.viewCenter` 为空 → 相机飞到气象站 → "模型加载出来但看不到/在远处"；旧 A 锚点代码路径若被命中 → 模型偏东 7.4km。这正是历史"模型飞到欧洲/错位"bug 的根因。

**修复建议**：
1. 删除 `ZHENGZHOU_STATION_57083` 在 SuperMapSceneViewer.vue 的 import 与所有引用，兜底改为 `SUPERMAP_CGCS2000_ANCHOR.wgs84`。
2. 清除 line 671-697 硬编码 113.569463，统一引用 `SUPERMAP_CGCS2000_ANCHOR`。
3. `ZHENGZHOU_STATION_57083` 仅保留作天气查询定位（语义改为 `ZHENGZHOU_WEATHER_STATION`），禁止用于 3D 场景锚点。
4. 以 `SUPERMAP_CGCS2000_ANCHOR` 为唯一权威，D 锚点（iServer 数据）若仍需则显式命名 `ISERVER_DATA_ANCHOR_D` 并注释与园区主锚点的关系。
5. `.env` 的 `VITE_QWEATHER_LOCATION` 保留气象站值但重命名语义清晰（天气定位 ≠ 园区定位）。

## 三、MEDIUM 详述

### 【M·4】DB 默认密码 123456 兜底
`backend/src/main/resources/application-local.yml:7` → `password: ${SPRING_DATASOURCE_PASSWORD:${DB_PASSWORD:123456}}`。本地 dev 可接受，但部署若忘设环境变量，弱密码 123456 直接上线。建议生产 profile 强制无默认值（缺失即启动失败）。

### 【M·5】登录接口缺密码长度上限
`LoginServiceImpl.java`：`register` 有 `MAX_PASSWORD_BYTES=1024` 校验（防 Argon2/bcrypt 高耗 DoS），`login` 无。攻击者用超长密码登录可触发哈希高耗。建议 `login` 起始同样 `validatePasswordLength`。

### 【M·6】依赖版本偏旧
`backend/pom.xml`：
- `jjwt 0.11.5` → 建议 0.12.x（0.11.x 已停维护）
- `bcprov-jdk18on 1.78.1` → **CVE-2024-30171**（RSA 时序）、**CVE-2024-30172**（Ed25519 死循环），1.79 修复
- `fastjson 2.0.42` → 2.0.47+ 修过多起反序列化问题（本项见下条）

### 【M·7】fastjson 死依赖
pom.xml 引入 `com.alibaba:fastjson 2.0.42`，但 `grep -rn fastjson backend/src/main/java` **零引用**。徒增反序列化风险面与包体积。建议直接移除该依赖。

### 【M·8】mapMetersPerUnit 四源并存
`supermapGeoreference.js:15`(SUPERMAP_MAP_SIZE=1)、`supermapCupScenario.ts:120`(=1，注释"0.5→1.0 对齐")、`.env VITE_SUPERMAP_MAP_METERS_PER_UNIT=1`、`SuperMapSceneViewer.vue:3545`(硬编码 1)。当前已全部对齐 1.0（历史 0.5 vs 1.0 漂移已修），但四处来源仍易再次漂移。建议单一来源 + 其余引用之。

### 【M·9】算法 API key 明文比较
`algorithm/service_config.py:67` `if provided_key != api_key` 非常量时间比较，存在时序侧信道。API key 时序敏感度低于密码，但建议 `hmac.compare_digest`。

上一会话工作树 `.env.development` 曾含 `VITE_QWEATHER_API_KEY = [REDACTED_SECRET]`（VITE_ 前缀会进客户端 bundle）。现已清空（Codex 已修，注释"天气密钥必须由后端持有"）。`git log -S` 确认该密钥**从未进入 git 历史**，`.env/.env.local/.env.*.local` 已被 .gitignore 正确忽略。风险已基本闭环，但该和风 key 曾在 dev bundle 暴露，**建议在和风控制台轮换该 key**。

## 五、审核通过项（无问题）

**后端 Java**：
- SQL 全参数化（`#{}`），无 `${}` 拼接；`TaskMapper.xml` LIKE 用 `CONCAT('%', #{keyword}, '%')` 安全；无循环内查询。
- JWT：密钥走 `JWT_SECRET` 环境变量，<32 字符 fail-fast（`JwtUtils.java:24-29`），`parseClaimsJws` 验签，无 `alg=none` 漏洞，24h 过期。
- 登录防时序攻击：`DUMMY_PASSWORD` 常量时间分支（`LoginServiceImpl.java:34-37`）；Argon2id 加密（spring-security-crypto + BC）；register 限密码 1024 字节。
- 鉴权架构干净：`WebConfig.java` `TokenInterceptor` 拦 `/api/**`，仅放行 `/api/auth/login`、`/api/auth/register`、`/api/sensor-readings/stream`（SSE 只读，注释说明）；`AdminAuthInterceptor` 注解驱动 `@RequiresRole`，不再维护离散路径白名单（注释明确指出这是旧越权根因已消除）。
- CORS：`CorsConfig.java` 限定具体域名（cip.lab6119.xyz），非通配；`allowCredentials=true` 配合具体 origin 安全。
- 无硬编码密码/密钥（`DUMMY_PASSWORD` 是时序攻击诱饵，非真实凭证）；无 eval/反射注入；无空 catch。
- 密钥卫生：`.env` 密钥已移出，`ALGORITHM_API_KEY` 走 `.env.development.local`（gitignore），`git log -S` 确认真实密钥从未入库。

**算法 Python**：
- 每个 REST 路由均挂 `dependencies=[Depends(require_api_key)]`（`api_server.py` 10 个路由全覆盖），X-API-Key 鉴权集中 `service_config.py`。
- `except Exception:` 均配 `logger.exception(...)` + 返回错误响应（`api_server.py:375/443`），**非静默吞**。
- 无 `eval()/exec()/shell=True/pickle.load/yaml.load`（`model.eval()` 是 PyTorch 评估模式，非代码执行，误报已排除）。
- 输入 CRS 白名单校验（`api_server.py:403-411`）。
- CORS 由 `install_algorithm_cors` 集中配置。

**前端 TS/Vue**：
- **0 个 `any`/`@ts-ignore`/`as any`/`@ts-nocheck`**（类型纪律优秀）。
- 无 `v-html`/`innerHTML`/`dangerouslySetInnerHTML`（无 XSS 注入面）。
- 空间查询纯函数 `geoQueryUtils.ts` 有 16/16 Node 单测。
