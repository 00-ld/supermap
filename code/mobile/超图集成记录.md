## 二、超图集成点清单（按实现顺序追加）

### 【集成点 1】许可初始化（App.java）—— ✅ 已实现
- **位置**：`app/src/main/java/com/at/mobile/App.java`
- **用到超图**：`com.supermap.data.Environment`、`com.supermap.data.LicenseStatus`
- **做法**：assets/License/*.slm 拷到 /sdcard/SuperMap/License/ → `Environment.setLicensePath()` + `Environment.initialization(this)` → `Environment.getLicenseStatus().isLicenseValid()` 校验
- **参考**：iMobile 2026 示例 `mobilegis/MyApplication.java` + `frequentlyopenmap/MainActivity.java`

### 【集成点 2】加载 iServer REST Map 在线底图（SuperMapHelper + MapActivity）—— ✅ 已实现（真机验证通过）
- **位置**：`app/src/main/java/com/at/mobile/map/SuperMapHelper.java`
- **用到超图**：`com.supermap.data.Workspace`、`DatasourceConnectionInfo`、`EngineType.Rest`、`com.supermap.mapping.MapView`、`MapControl`、`Map`、`Datasource`
- **做法**（2026-07-22 真机验证修复版，完整园区底图已呈现建筑/道路/设施点）：
  ```java
  // 工作线程打开数据源（网络 IO）
  DatasourceConnectionInfo info = new DatasourceConnectionInfo();
  info.setEngineType(EngineType.Rest);          // ← 关键：Rest 引擎加载标准 iServer REST Map
  info.setServer(config.getMapUrl());          // ← 中文已预编码 %XX（见坑 10）
  info.setAlias("parkMap");
  Datasource ds = workspace.getDatasources().open(info);
  final int datasetCount = ds.getDatasets().getCount();
  // 主线程叠加全部数据集（只加 get(0) 会只有道路，见坑 11）
  mapView.post(() -> {
      Map map = mapControl.getMap();
      for (int i = 0; i < datasetCount; i++) {
          map.getLayers().add(ds.getDatasets().get(i), true);
      }
      map.viewEntire();
      map.refresh();
  });
  ```
- **参考**：iMobile 2026 示例 `iportalunity/MapViewFragment.openRestMap()`（line 72-84）
- **废弃方案**：`mapoverlay` 示例用的是 `EngineType.OpenGLCache` + `/rest/OpenGLTile`（MVT 矢量瓦片），该示例官方标注"该示例存在问题，暂时废弃"，且园区发布的是标准 REST Map 而非 MVT，故不采用。

### 【集成点 3】地图叠加事故/任务/巡检车点（SuperMapHelper.addTaskMarkers / addCarMarkers）—— ✅ 已实现
- **位置**：`app/src/main/java/com/at/mobile/map/SuperMapHelper.java`（addTaskMarkers/addCarMarkers/clearTag/taskStyle/warningStyle）
- **用到超图**：`com.supermap.mapping.TrackingLayer`、`com.supermap.data.GeoPoint`、`GeoStyle`、`Point2D`、`Size2D`、`Color`
- **做法**：在 REST 底图之上用 TrackingLayer 叠加动态业务点位，无需建数据集。`trackingLayer.add(geoPoint, "task:"+id)` 加点，`geoPoint.setStyle(geoStyle)` 设样式，`clearTag(layer,"task:")` 增量刷新避免重复。状态颜色映射：红=处置中/橙=已指派/黄=待验收/绿=已完成/灰=已取消/蓝=待指派；巡检车 warning=1 红、正常绿。
- **MapActivity 接入**：地图 onLoaded 后并行拉 `listTasks(null)` + `getAllCars()`，分别叠到 TrackingLayer，接口失败不影响底图。
- **参考**：iMobile 2026 示例 `trackingmap/MainActivity.java`（line 166-180）确认 `trackingLayer.add(geoPoint, tag)` + `GeoStyle.setMarkerSize/setMarkerSymbolID/setFillForeColor` 用法。
- **踩坑**：`GeoStyle` 无 `setMarkerColor(Color)` 方法（编译报错见坑 7），点符号颜色实由 `setFillForeColor` + `setMarkerSymbolID(351 圆点)` + `setFillOpaqueRate(100)` 控制。

### 【集成点 4】GPS 定位点同步到地图坐标（CoordTransform）—— ⏳ P2 部分实现
- **用到超图**：`com.supermap.data` 坐标系与投影 API
- **背景**：园区 iServer 地图是 PCS_NON_EARTH 本地米制（epsgCode=-1000），GPS 给的是 WGS84 经纬度，需换算到本地米制才能在图上打点。
- **P2 进展**：打卡 GPS 存 WGS84 经纬度到 `task.checkin_x/y`（首版方案，落库不阻塞闭环）。地图层叠加用的是后端 task.x/y 与 patrol_car.x/y（园区本地米制，与底图同坐标系直接打点）。移动端 WGS84→本地米制的 `CoordTransform` 移植自网页端 `supermapGeoreference.js` 锚点公式，留待 P3 优化（当前打卡仅落库不在地图打 GPS 点，故不阻塞）。

## 三、超图优点（实测）

1. **在线 REST 地图加载极简**：`EngineType.Rest` + `DatasourceConnectionInfo.setServer(restUrl)` 一行打开 iServer 标准 REST Map，无需离线数据，移动端是真正的 thin client。相比自研瓦片方案省去了瓦片切片/存储/分发整套链路。
2. **SDK 与 iServer 服务端一体化**：iMobile 与 iServer 同出自超图，坐标系、数据格式（SMWU/UDB）、服务接口天然对齐，前端 .env 里配的 iServer URL 移动端可直接复用，零适配成本。
3. **示例库覆盖全**：80+ 官方示例（地图/采集/轨迹/标绘/定位/数据服务/网络分析），几乎每个业务场景都能找到对应范式代码，对照即可用。
4. **License 机制轻量**：.slm 文件随 APK assets 打包，运行时拷贝到 sdcard 即可激活，无需联网激活，适合离线/弱网现场处置场景。
5. **坐标范围可直接查询**：iServer REST 返回的 map JSON 带 `viewBounds`/`center`/`prjCoordSys.epsgCode`，移动端初始视角和坐标换算所需的边界值一次 curl 就能拿到，不用猜。

## 四、超图缺点与坑（实测）

1. **示例质量参差**：`mapoverlay` 示例（iServer REST 叠加）官方标注"存在问题，暂时废弃"，且用的是 OpenGLCache（MVT 引擎），与标准 REST Map 不匹配——直接照搬会导致加载失败。必须交叉验证多个示例才能找到正确 API（最终在 `iportalunity/MapViewFragment` 找到正确写法）。
2. **仅支持 armeabi-v7a**：iMobile 2026 SDK 全盘无 arm64-v8a，`abiFilters` 只能配 armeabi-v7a。在 64 位-only 的新安卓设备上需依赖系统的 32 位兼容，部分新机型（如纯 64 位 Android 14+）可能无法运行。
3. **SDK 版本绑定旧工具链**：要求 compileSdk 28 / minSdk 24 / JDK 1.8 / AGP 3.6.3 / Gradle 5.6.4，无法用最新的 AGP 8 + Gradle 8 + compileSdk 34，与主流新工程混编困难，新 AndroidX 库版本受限（appcompat 只能 1.0.2）。
4. **依赖本地 jar/aar，不走 Maven**：SDK 以 `fileTree(dir:'libs', include:['*.jar'])` 引入，20+ jar 与 25 个 .so 体积大（APK 至少 80MB+），且升级需手动替换文件，无法通过版本号自动管理依赖。
5. **坐标系不透明**：园区 iServer 地图实际发布的是 `PCS_NON_EARTH`（epsgCode=-1000，平面非地球米制），与 .env 里注释的 CGCS2000(EPSG:4547) 名实不符。前端 .env 的锚点坐标(469313.780,3843337.292) 与 iServer 实际 viewBounds(457091.92~459999.97, 3854317.55~3857225.59) 完全对不上——必须以 iServer REST 返回的实际值为准，不能信配置文件注释。
6. **文档与 API 对不上**：iMobile 加载 iServer REST Map 的正确 `EngineType.Rest` 写法散落在 `iportalunity` 示例里，官方 API 文档没有集中说明，靠 grep 全局搜索示例才定位到。
7. **试用 License 时效未知**：`SuperMap iMobile Trial.slm` 是试用许可，到期时间不透明，需长期关注是否失效影响交付。

## 五、踩坑记录（按时间）

### 坑 1：mapoverlay 示例废弃导致地图加载方案一度走错
- **现象**：最初参考 `mapoverlay/MainActivity.java`，用 `EngineType.OpenGLCache` + `/rest/OpenGLTile` URL。
- **排查**：发现该文件头注释"该示例存在问题，暂时废弃"；且 `/rest/OpenGLTile` 是 MVT 矢量瓦片端点，园区发布的 `map-chemical_park_vectors_cgcs2000/rest` 是标准 REST Map，二者不匹配。
- **解决**：grep 全局搜索，在 `iportalunity/MapViewFragment.openRestMap()` 找到正确写法 `EngineType.Rest`，URL 指向完整 REST Map 路径（含地图名）。验证通过 iServer `services.json` 确认服务类型为 `RestServlet`。

### 坑 2：园区坐标系名实不符
- **现象**：.env 注释写 CGCS2000 / EPSG:4547，锚点 469313.780,3843337.292。
- **排查**：curl iServer REST Map 的 map.json，返回 `prjCoordSys.epsgCode=-1000`、`name=PCS_NON_EARTH`、`coordUnit=METER`，实际 viewBounds 是 457091~459999, 3854317~3857225。
- **解决**：移动端 config.properties 的 map.bounds 与 map.center 以 iServer 实际返回值为准；GPS 定位点换算用本地米制锚点，不用 CGCS2000 投影。SuperMapHelper 最终用 `map.viewEntire()` 自适应数据范围，不硬编码 setViewBounds，规避了范围不匹配风险。

### 坑 3：iMobile SDK 绑定旧工具链，与高版本 JDK 死磕（编译环境最大坑）
- **现象**：iMobile 2026 SDK 示例用 AGP 3.6.3 + Gradle 5.6.4 + compileSdk 28 + JDK 1.8。本机只有 JDK 21/23/25，无 JDK 8/11。
- **排查链**：
  - Gradle 5.6.4 + JDK 25 → `Unsupported class file major version 69`（Groovy 不认 JDK 25）
  - Gradle 7.6.3 + AGP 7 → 同样不支持 JDK 25
  - Gradle 8.14.3 支持 JDK 21，但 AGP 7 要求 compileSdk 30+
- **解决**：最终选 **AGP 8.5.2 + Gradle 8.14.3 + compileSdk 34 + JDK 21**（gradle.properties 指定 `org.gradle.java.home=C:/Program Files/Java/jdk-21`），minSdk 26 / targetSdk 28 保持 iMobile 约束。AGP 8 用高 compileSdk 构建低 targetSdk 工程，向下兼容 iMobile jar。
- **代价**：minSdk 从 24 提到 26（log4j-core 2.12.4 用 MethodHandle 需 min-api 26），覆盖 97%+ 设备，可接受。

### 坑 4：SDK 自带 jar 与 Maven 依赖重复 class
- **现象**：SDK 的 gson-2.2.2.jar、okhttp-4.12.0.jar、okio-1.13.0.jar 与 Retrofit 2.11 / logging-interceptor 4.12.0 传递的同名依赖冲突，`checkDebugDuplicateClasses` 报 Duplicate class。
- **解决**：删 SDK 的 gson-2.2.2.jar（用 converter-gson 带的 gson 2.10.1）、okhttp-4.12.0.jar、okio-1.13.0.jar（用 Maven 4.12.0 同版本自动去重）。保留 iMobile 核心 jar（com.supermap.*_v1210）不动。

### 坑 5：iMobile MapView 继承 RelativeLayout 非 GLSurfaceView
- **现象**：代码审查建议给 MapActivity 加 `mapView.onPause()/onResume()/onDestroy()`，编译报"找不到符号"。
- **排查**：javap 查 iMobile MapView，`public class MapView extends android.widget.RelativeLayout`，无 GL 生命周期方法。mobilegis 示例 MainActivity 也未 override 这些。
- **解决**：去掉 mapView 的 onPause/onResume/onDestroy 调用，资源释放只靠 SuperMapHelper.dispose()（map.close → workspace.dispose → mapControl.dispose 顺序，对齐官方示例）。
- **教训**：代码审查的建议要结合 SDK 实际 API 验证，不能照搬通用 Android 假设。

### 坑 6：Environment 简名冲突（com.supermap.data vs android.os）
- **现象**：App.java 同时 import `com.supermap.data.Environment` 和 `android.os.Environment`，编译报"对 Environment 的引用不明确"。
- **解决**：com.supermap.data.Environment 的调用改用全限定名 `com.supermap.data.Environment.setLicensePath(...)`，android.os.Environment 保留 import 简用。

### 坑 7：GeoStyle 点符号无 setMarkerColor 方法（P2 叠加点位首次编译失败）
- **现象**：`SuperMapHelper.addTaskMarkers` 首版用 `style.setMarkerColor(new Color(...))` 设点颜色，编译报"找不到符号 方法 setMarkerColor(Color)"。
- **根因**：iMobile 的 `GeoStyle` 没有 `setMarkerColor`，点符号颜色实际由填充色控制——`setFillForeColor(Color)` + `setFillOpaqueRate(int)` + `setMarkerSymbolID(351 内置圆点)`。
- **解决**：改用 `setFillForeColor` 设色 + `setMarkerSymbolID(351)` 圆点符号 + `setFillOpaqueRate(100)` 不透明。对照 `BoundsQuery/MainFrame.java`（line 229-232）确认。
- **教训**：iMobile 点/线/面样式 API 分散，点颜色不在"Marker"族而在"Fill"族，与直觉相悖；写叠加代码前必须 grep 示例确认 setter 签名。

### 坑 8：iMobile 许可目录选型——/sdcard 在 Android 10 scoped storage 下不可写
- **现象**：早期版本按官方示例用 `/sdcard/SuperMap/License/`，Android 10+ scoped storage 下该路径需 WRITE_EXTERNAL_STORAGE 运行时权限且可能被系统拒绝，许可文件拷不过去 → `isLicenseValid()=false`。
- **排查**：`getExternalFilesDir(null)` 是应用私有外部目录，Android 10+ 无需任何存储权限即可读写，且系统不会扫描其中的媒体文件。
- **解决**：许可目录改用 `getExternalFilesDir(null)/SuperMap/License/`，assets 里的 `.slm` 递归拷贝到此目录；同时 `Environment.setTemporaryPath` / `setWebCacheDirectory` 也预先指向 `getExternalFilesDir(null)/SuperMap/temp|data/`，防止 `initialization` 内部默认指向不可写的 `/sdcard/SuperMap/`。App.java 实测 `SuperMap license valid = true`。
- **教训**：iMobile 官方示例的 `/sdcard/` 路径是 Android 6 时代的写法，在 Android 10+ 上必须改用应用私有目录；`initialization` 内部会回写默认路径，需在调用前显式覆盖。

### 坑 9：试用许可激活——手机系统时间必须改到 2019
- **现象**：`SuperMap iMobile Trial.slm` 是限时试用许可，许可文件内的签发/有效期基于真实日历时间。手机当前系统时间若晚于许可有效期，`isLicenseValid()` 返回 false，地图组件全部不可用。
- **排查**：将手机系统时间手动调到 **2019-08-01** 后，许可状态变为 valid。说明该试用许可的有效期窗口在 2019 年附近。
- **解决**：备用机系统时间固定设为 2019-08-01，App.onCreate 日志确认 `license valid = true`。正式交付需向超图申请正式授权许可（见坑 9 待评估项）。
- **副作用与连带坑**：改系统时间到 2019 会导致 HTTPS 证书校验"证书未生效"（见坑 10），整个网络层必须绕开 HTTPS。

### 坑 10：2019 系统时间 vs iServer HTTPS 证书——TLS 握手必死
- **现象**：手机时间改成 2019 后，访问原公网域名 `https://www.chemgas.lab6119.xyz/iserver`（443 HTTPS）TLS 握手失败，报"证书未生效/SSLHandshakeException"。iServer 在 2019 时间点被判定证书未到生效期。
- **排查**：证书的有效期起点晚于 2019，手机系统时间早于证书 notBefore → TLS 校验直接拒绝。OkHttp 默认信任系统 CA 且强制校验时间窗，无法通过。
- **解决**：iServer 改走 **HTTP 18090 端口直连**（`http://8.130.175.232:18090/iserver`），绕开 HTTPS 证书校验。18090 是 nps 公网映射的纯 HTTP 端口，2019 时间下可达。`config.properties` 的 `iserver.baseurl` / `iserver.map.url` / `iserver.data.url` 全部用 HTTP 18090。
- **代价**：HTTP 明文传输，仅限备用机+公网 iServer 场景；正式环境必须恢复手机正确时间 + 走 HTTPS + 申请覆盖真实时间窗的许可。
- **教训**：试用许可改系统时间是个连锁坑——时间改了，HTTPS 就废了；移动端 GIS 试用场景必须准备 HTTP 兜底通道。

### 坑 11：iMobile Rest 引擎对 setServer URL 中的中文不做 URL 编码
- **现象**：地图名含中文（`建筑单体校核图_CGCS2000`），直接传原始中文给 `info.setServer(url)`，iMobile 内部拼接 `.xml` 请求时**不做 URL 编码**，中文字节被 iServer 当成乱码地图名 → 404 → 报"读取XML信息失败"。
- **排查**：抓包对比 iMobile 发出的请求 URL，中文仍是原始 UTF-8 字节，未转义为 `%XX`。iServer 收到非 ASCII 字节解析地图名失败。
- **解决**：`config.properties` 的 `iserver.map.url` 预先把中文编码为 `%XX`（UTF-8）：`%E5%BB%BA%E7%AD%91%E5%8D%95%E4%BD%93%E6%A0%A1%E6%A0%B8%E5%9B%BE_CGCS2000`，iMobile 原样透传，iServer 正确解码找到地图。
- **教训**：iMobile Rest 引擎对 URL 的处理是"透传不编码"，凡 setServer 的 URL 含中文/特殊字符，必须在传入前自行 URL-encode；不能假设 SDK 会像浏览器/Retrofit 那样自动转义。

### 坑 12：iServer 数据源含多个数据集——只加 get(0) 只显示道路看不到建筑物
- **现象**（用户反馈"现在能显示了，但这个是道路的 data 服务吧，都看不到建筑物"）：地图首次加载只看到黄色道路线，园区建筑、设施点、入口点全没有。
- **排查**：
  - `curl` iServer map 服务 JSON → `layers count=0`（map 服务本身不暴露图层列表）
  - `curl` iServer data 服务 JSON → 7 个数据集：`Park_RoadPolygon_R`（道路面）、`Park_RoadNetworkNode_R`/`Park_RoadNetworkEdge_R`（路网点边）、`Park_BuildingFacilityPolygon_R`（建筑设施面）、`Park_BuildingFootprint_R`（建筑 footprint）、`Park_EntrancePoint_R`（入口点）、`Park_S3MObjectFootprint_R`（三维 footprint）
  - 旧代码 `ds.getDatasets().get(0)` 只取第 0 个（RoadPolygon = 道路），建筑在第 3/4 个数据集，自然不显示
- **解决**：`SuperMapHelper.loadParkMap` 改为遍历全部数据集叠加：
  ```java
  final int datasetCount = ds.getDatasets().getCount();
  mapView.post(() -> {
      Map map = mapControl.getMap();
      for (int i = 0; i < datasetCount; i++) {
          map.getLayers().add(ds.getDatasets().get(i), true);
      }
      map.viewEntire(); map.refresh();
  });
  ```
  重建 APK 重装后截图 `_screenshots/map_all_layers.png`（180KB，vs 旧版 38KB）确认建筑(灰色多边形)+道路(黄线)+设施点全部呈现。
- **教训**：iServer 的 map 服务与 data 服务是两套——map 服务返回的 `layers` 可能为空，真正的图层信息在 data 服务的 datasets 列表里；iMobile 加载 Rest 数据源后必须遍历 `Datasource.getDatasets()` 全部叠加，不能只取首个。示例代码 `getDatasets().get(0)` 是最小 demo 写法，生产环境要按数据集个数循环。

### 坑 13：admin 账户密码哈希缺前缀——DelegatingPasswordEncoder NoOp 降级失败
- **现象**（用户要求"账户改为 admin，密码 123456"）：移动端用 admin/123456 登录返回 401"用户名或密码错误"，但 mobileadmin/123456 能登录。
- **排查**：查 `user` 表，admin (id=4) 的 password 是 `$2a$10$...`（BCrypt）**无 `{bcrypt}` 前缀**；后端用 `DelegatingPasswordEncoder`，无前缀的哈希会走 NoOp fallback 做**明文比较**，BCrypt 密文 ≠ 明文 "123456" → 失败。而 mobileadmin 的 password 是 `{argon2id}$argon2id$v=19$m=16384,t=2,p=1$...`，前缀匹配 Argon2 编码器，校验通过。
- **解决**：把 mobileadmin 的 argon2id 哈希（即 "123456" 的哈希）复制给 admin：
  ```sql
  UPDATE user SET password='{argon2id}$argon2id$v=19$m=16384,t=2,p=1$7kkBAFTTUzpOyvpBhtGMWQ$33NpT2Hw0jifHrVRGRUxSkoJTy1bW/qt3fYYMlN7PbU' WHERE username='admin';
  ```
  验证 admin/123456 登录 → 200 OK 拿到 token。
- **教训**：`DelegatingPasswordEncoder` 的无前缀 fallback 是明文比较，不是"猜编码器"——历史遗留的裸 BCrypt/MD5 哈希会静默失效。迁移账户时必须显式带 `{bcrypt}`/`{argon2id}` 前缀，或直接用当前默认编码器重新哈希。这虽是后端通用问题，但移动端登录首当其冲暴露。

### 11.3 坑 14：DataDownloadService 依赖废弃的 Apache HttpClient → NoClassDefFoundError 崩溃

**现象**：`DataDownloadService.downloadDataset` 调用后无任何回调（`dataServiceFinished`/`requestFailed` 都不触发），app 卡在 loading 转圈。日志里其实是下载线程直接崩了：
```
FATAL EXCEPTION: Thread-13
java.lang.NoClassDefFoundError: Failed resolution of: Lorg/apache/http/params/BasicHttpParams;
    at com.supermap.services.ServiceBase.isUrlDatasetExisted(ServiceBase.java:380)
    at com.supermap.services.DataDownloadService.downloadDatasetFromServer(DataDownloadService.java:521)
Caused by: java.lang.ClassNotFoundException: org.apache.http.params.BasicHttpParams
```

**根因**：SuperMap `services` 包内部仍用已废弃的 `org.apache.http.*`（Apache HttpClient），而 `targetSdkVersion 28` 默认不再打包该库到 APK，运行时类找不到直接崩。`DataDownloadService` 的下载线程在 `run()` 里抛 `NoClassDefFoundError`，没进任何回调，所以表现为"回调不触发"。

**解决**：`app/build.gradle` 的 `android {}` 块加一行：
```gradle
useLibrary 'org.apache.http.legacy'
```
显式引入 Android 内置的 `org.apache.http.legacy` 静态库（API 28 仍支持），SDK 内部 Apache HTTP 调用即可恢复。

**教训**：SuperMap iMobile 2026 SDK 的 `services` 包（DataDownloadService / GetFeatureService 等）仍停留在 Apache HttpClient 时代。凡是用到 `com.supermap.services.*` 的网络类，`targetSdk≥28` 的工程都必须 `useLibrary 'org.apache.http.legacy'`，否则运行时崩。这是 SDK 层历史包袱，非代码能绕开。

### 12.7 坑 15：GeoCircle 毒气扩散圈 native crash

**现象**：地图叠加任务点位后，processing/assigned 状态的任务会触发 `addDiffusionZone` 用 `GeoCircle` 画 150m 半径圆，多个任务时偶发 native crash，日志无 Java 栈，直接 SIGSEGV。

**根因**：iMobile 2026 SDK 的 `com.supermap.data.GeoCircle` 在 TrackingLayer 叠加时稳定性差，且原实现 `clearTag(layer, "task:")` 无法清除 `"diffusion:"+x+"_"+y` tag 的圆，导致每次 `addTaskMarkers` 刷新时扩散圆累积，圆数量增长加剧 native 崩溃概率。

**解决**：直接删除 `addDiffusionZone` 方法及调用。任务点位用 `GeoPoint` + `setFillForeColor` 圆点符号（351）足够表达状态色，扩散范围由后端浓度场计算，移动端不重复画。

**教训**：iMobile 的 `GeoCircle`/`GeoRegion` 等复杂几何体在 TrackingLayer 叠加时性能与稳定性都不如 `GeoPoint`，生产环境动态叠加应优先用点符号，复杂面留给底图数据集。
